# 物联网与售后一体化：需求与实施建议 V1

日期：2026-11-07。本文保留最初需求规划；首期模拟版本的实际实现、验证和未完成范围见 [delivery-v1.md](delivery-v1.md)，不能将本需求表等同于全部已交付。

## 1. 本轮结论与范围

现阶段使用同一代码仓库和现有产品入口，物联网单独划分业务模块、采集进程和数据存储边界；共用企业、账号身份和权威设备档案。以后可将物联网迁往独立服务，页面入口与设备身份不必重建。

产品有四个原有端，但新增企业手机工作台后，需按五种使用场景设计：维保云平台、企业桌面后台、企业手机模式、普通客户模式、工程师端。企业手机模式复用 3101 用户应用，不立即新建第五个端口、独立 App 或小程序。

这里的企业手机模式首先指入驻企业的管理员及获授权员工。设备使用方公司的多人管理，可沿用组织授权思路扩展，但不能与入驻售后服务企业混为一种身份。

首期以监测、告警、人工确认转工单为主；远程开停机、参数修改、OTA、自动维修诊断、自动收付款不纳入首期。

## 2. 已核实的现有基础

- 企业后台 React：apps/cs-admin；平台：apps/platform-admin-web；客户和工程师分别在 apps/customer-app-web、apps/engineer-app-web。
- 后端已存在 identity、platform、tenancy、market 等模块，有统一个人登录、企业账号密码登录、企业成员关系、套餐 features、租户隔离和 Socket.IO 基础。
- 设备二维码已有稳定的 identity.assets.id；客户/市场页面使用的 identity.resources.id 是另一套资源引用，必须建立转换，不能把两个 UUID 直接混用。
- 当前客户登录显式请求 customer 身份；不能仅加一个前端判断就让企业手机模式安全上线。需要补充服务端身份发现、企业成员授权及设备访问范围。
- 原三类售后团队已有组织和委托关系；设备归属、当前承接企业、实际工程师必须继续分开记录。
- 本次未发现已实现的完整物联网采集、监测存储和告警规则模块；这些属于新增开发，不是替换几张图表。

| PL-04 | 维保云 | P0 | 为企业开通/停用物联网，配置设备接入上限、有效期与历史数据策略 | 菜单、查询、订阅、接入凭证均检查策略；停用不悄悄删除历史记录 |

| B-01 | 企业桌面 | P0 | 本企业设备总览、在线/离线/告警筛选、安装地点、客户关联 | 只看本企业有权设备；服务商不能默认读取委托方全部设备 |
| B-02 | 企业桌面 | P0 | 设备详情加实时参数、更新时间、质量状态、趋势和告警记录 | 每个指标有名称、单位、时间；“已售出”不误当“已接入”；未开通与未接入有独立空态 |
| B-03 | 企业桌面 | P0 | 接入管理：指标模板、设备凭证发放/轮换、网关与设备映射 | 二维码是档案标识，不是设备上传密钥；前端不得拿到全平台接入密钥 |
| B-04 | 企业桌面 | P0 | 告警列表、确认/恢复/处理说明、人工转工单并关联客户 | 同一告警重复通知不得重复建单；有客户、无客户、无地址均有明确处理路径 |
| B-05 | 企业桌面 | P0 | 企业管理员授权员工、配置设备组/厂区的可见范围 | 员工移除后，已有实时连接与接口访问同时失效 |
| B-06 | 企业桌面 | P1 | 管理历史数据、告警阈值、导出、通知偏好 | 数据保留与套餐一致；阈值及规则变更留记录 |
| MB-01 | 企业手机 | P0 | 统一登录后依据服务端授权进入企业工作台；显示企业名称、角色、设备概览 | 单一身份自动进入；多身份/多企业选择一次并可切换；不能由前端自封企业身份 |
| MB-02 | 企业手机 | P0 | 企业设备列表、设备详情、关键参数、趋势、告警确认与待办 | 复用企业桌面的权限与数据；切换企业清掉旧列表和实时订阅 |
| MB-03 | 企业手机 | P0 | 扫设备二维码进入有权限的监控页 | 扫码不自动转移设备，不因持有二维码获得企业权限 |
| MB-04 | 企业手机 | P1 | 企业成员管理、设备分组、较完整的运营统计 | 复杂接入配置、批量导出先保留桌面入口 |
| C-01 | 普通客户 | P0 | 自己绑定设备的状态、有限指标、异常提示与报修入口 | 只显示被允许给客户看的指标；普通客户不能看到全国/企业全部设备 |
| C-02 | 普通客户 | P0 | 异常一键报修，携带确定的设备和告警摘要 | 不再让用户重复选择同一设备；不把报警直接宣称为确诊故障 |
| C-03 | 普通客户 | P1 | 设备状态变化提示、通知偏好 | 短信、公众号、小程序订阅消息需要独立资质和配置，不能承诺网页有原生后台推送 |
| E-01 | 工程师 | P0 | 报修设备详情展示关键监测值、最后上报时间、故障前后曲线和告警时间线 | 权限来自具体任务/授权；自有、外包、平台工程师都不能随意浏览企业全部数据 |
| E-02 | 工程师 | P0 | 工单保留报修时数据快照，维修前后对比与处理说明 | 持续变化的实时数值不能覆盖历史证据；取消/转派后按规则撤销访问 |
| E-03 | 工程师 | P1 | AI 助手可引用有权限的监测摘要，辅助分析 | 显示数据来源与时间；数据不足时明确提示，不自动作出确定性维修结论 |

## 5. 共用基础需求

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| CORE-01 | P0 | 一份权威设备档案；iot.asset_id 关联 identity.assets.id，兼容租户本地 device.id 与 identity.resources.id 的转换 |
| CORE-02 | P0 | 指标模型记录字段名、单位、数据类型、范围、可见性；温度/电流等只是候选，实际字段由设备资料决定 |
| CORE-03 | P0 | 接收设备数据并验证凭证，服务端推导租户归属；禁止设备请求任意指定另一个租户 |
| CORE-04 | P0 | 同时保留设备采集时间和服务器接收时间，处理乱序/重复/异常值；失去心跳后状态转为离线，不能一直显示最后一次的正常值 |
| CORE-05 | P0 | 实时通道复用已有 Socket.IO 基础，但为物联网独立命名空间；订阅由服务端授权，具备断线重连和最新状态补取 |
| CORE-06 | P0 | 告警由阈值、持续时间与恢复条件判定；重复合并、恢复记录、通知失败重试；转工单携带唯一告警 ID，保持幂等 |
| CORE-07 | P0 | 模拟器与真实接入使用同一数据入口；演示设备、指标、全国分布均标记模拟；不以模拟运行宣称已接真机 |
| CORE-08 | P0 | 套餐开通、查询权限、实时订阅和工程师临时授权的统一校验与审计 |
| CORE-09 | P0 | 设备安装地点及坐标来源；无位置可登记省市但不伪造定位；地图聚合和列表口径一致 |
| CORE-10 | P1 | 写入量、错误率、延迟与存储用量监测，数据保留与聚合归档策略、备份与恢复 |

“实时”需要约定：建议首轮页面按 2–5 秒合并刷新，接入端上报频率按设备与指标配置。界面刷新频率不等于设备采样频率。初始负载方案可暂按 1,000 台、10 秒上报一次估算，约 100 条设备消息/秒；这是待确认的设计假设，不是压测结论。

在线/离线、运行/停机、正常/告警是三组不同状态；运行与停机必须有实际数据依据，不用是否在线来替代。

## 6. 账号与权限方案

- 认证企业：平台核实并开通的租户组织；企业管理员邀请/授权人员。不是用户在登录页勾一个企业标签。
- 登录后的首页选择由服务端返回的可用身份、组织成员关系、开通功能和设备范围决定。
- 同时有个人客户、企业员工、工程师身份时，提供明确的身份切换；每种身份有独立权限范围，不把权限自动合并。
- 不让企业成员在手机端直接继承无约束的平台管理员能力；平台管理员依旧使用维保云入口。
- 现有企业桌面账号密码体系继续有效；手机登录可复用凭证或绑定经验证的个人账号。真实短信、微信登录需要另行接入，现有 000000 仅为演示。
- 切换身份/企业后撤销旧订阅并重新授权；解绑设备、撤销成员和工单转派后及时撤权。
- 第一版默认工程师只在有效任务及必要诊断时间范围内查看设备资料，具体历史时间窗口可配置；扩大权限需企业明确授权并留记录。

## 7. 数据联动与验收流程

设备/模拟器 -> 独立接入入口 -> 最新状态与历史数据 -> 规则判定 -> 告警事件 -> 售后告警待办 -> 人工确认生成对应流程工单 -> 原有自营/外包/平台路由 -> 工程师诊断和维修 -> 客户验收 -> 保留监测快照及处理记录。

售后策略在生成任务时按既有规则确定并形成快照。已有合同工单和平台市场服务单是两类现有业务对象，告警转单应明确选择既有流程，不能为同一故障创建两张互不关联的单据。

重试事件需带 eventId/alarmId；工单保存唯一来源映射，避免网络重试、重复点击或持续超限造成重复建单。识别到多个异常属于同一事故时，首期可人工关联到已有工单。

## 8. 代码边界建议（拟新增，尚未创建）

```text
backend/src/iot/                 业务查询、规则、权限、对外 API
apps/iot-ingest/                 独立采集进程、协议适配、模拟器
packages/iot-contracts/          指标与事件契约、版本、错误定义
apps/platform-admin-web/iot/     平台全国大屏与开通管理
apps/cs-admin/src/features/iot/  企业桌面监控
apps/customer-app-web/iot/       普通客户监控页面与共用轻量组件
apps/customer-app-web/business/  企业手机工作台与身份切换
apps/engineer-app-web/iot/       工单诊断视图
backend/test/iot-*.mjs           接入、隔离、角色、告警及跨端测试
```

当前几个静态端还存在集中脚本。新页面不继续往巨大的 market-ui.js 或 app.js 中堆积业务，只增加必要入口与适配。

物联网数据使用独立逻辑数据库/存储连接池，开发期可共用 PostgreSQL 实例；不让高频采集写入直接占满现有 registry 池或每个租户的工单连接。真实规模确认后再决定分区、时序扩展或专用时序库，不预先堆积不必要的组件。

- identity/platform 维护权威身份、租户与设备映射；iot 通过明确接口读取，不改写客户/工单归属。
- iot 维护监测记录和告警，不直接写售后工单表；通过适配层创建工单。
- 告警通知采用可重试、可去重的事件记录；初期可用数据库待发事件，不要求一上来部署大型消息集群。
- 协议适配器和业务规则分开；初期以 HTTP 模拟接入跑通，再按真实设备协议增加 MQTT/网关适配，不承诺所有激光设备都能无改造接入。
- 以后拆服务时，替换通信适配和部署位置；设备标识、权限规则与接口契约继续保留。

## 9. 分阶段工作量估算

以下为单人串行开发、现有代码可复用、首种设备模型范围有限的粗估工作量，不是小时级完成承诺。真实协议、现场设备、账号审批、稳定 HTTPS 部署及较大设计返工会影响日历时间。

| 阶段 | 交付内容 | 本阶段估算 | 累计估算/边界 |
| --- | --- | --- | --- |
| A 视觉与流程原型 | 平台全国大屏、企业监控首页、企业手机首页、客户设备页、工程师诊断页；使用标记的模拟数据 | 2–3 个工作日 | 可看布局与点击，不代表物联网已接入 |
| B 模拟业务闭环 | 独立接入模拟器、状态/趋势、套餐、企业手机身份、设备隔离、告警人工转单及三类售后权限 | 再 6–9 个工作日 | 累计约 8–12 个工作日 |
| C 业务验收与整改 | 五种场景点击验证、越权/撤权、断线/乱序、重复告警与重试、现有售后回归和有限负载验证 | 再 2–3 个工作日 | 首期可验收模拟版累计约 10–15 个工作日 |
| D 首种真实设备接入 | 在协议资料完整且设备/网关可用前提下，适配、现场连接、断网恢复和数据核对 | 暂估再 3–10 个工作日 | 私有协议、厂商权限或新增硬件需要重新评估；未确认前不能锁定日期 |
| E 对外试运行 | 固定 HTTPS 入口、部署、监控、备份、实际通知渠道及持续运行观察 | 单独评估，通常还需预留 1–2 周试运行窗口 | 不把免费公网隧道短时可访问当作生产验收 |

优先做 A 确认视觉，再做 B/C；不要一次把整个 ThingsCloud 功能集当成第一版。第一版不包含自定义拖拽大屏编辑器、3D 数字孪生、所有协议接入、远程控制、OTA、微信/原生 App 发布、自动财务结算和 AI 故障确诊。

## 10. 必须通过的验收场景

1. 企业 A/B 同名、同 SN 设备仍隔离；接口、导出和实时推送均不能越权。
2. 普通客户、企业员工、平台运营、三类工程师分别只看到授权范围；同一手机号多角色可正确切换。
3. 未开通、到期、停用、人员撤权均阻止查询/订阅；不通过隐藏菜单冒充权限控制。
4. 数据持续变化 -> 全国汇总、企业桌面、企业手机、客户和工程师视图按权限一致更新。
5. 断开上报 -> 最后上报时间可见 -> 超时转离线；旧数值不伪装实时值；重连补取最新状态。
6. 重复/乱序消息不回滚最新值；超范围数据标记异常，不用它直接确诊设备损坏。
7. 持续超限产生一条有效告警，恢复另有记录；网络重试和重复点击不重复创建维修单。
8. 扫码后企业用户进入授权监控、客户进入自己设备、陌生账号不可借二维码获得企业数据。
9. 工单转派/取消、设备解绑/变更客户后及时调整可见范围；旧工单保留当时的证据快照。
10. 省市地图、列表和总数一致，缺失地点不伪造；模拟数据和真实数据有明确区别。
11. 真机阶段实测设备上报、时间/单位、断网重连，核对历史与维修记录；只有模拟器不算真机交付。

## 11. 开发前需确认的材料

- 第一种接入设备的品牌、型号、控制器/网关型号及协议文档；是否已能输出数据。
- 第一批需要看的指标、单位、报警标准，是否有厂商代码表。
- 初期/一年设备数、上报频率与历史数据保留时间。
- 企业手机使用人员范围（管理员、客服、设备运营、客户企业负责人等）。
- 全国地图的位置来源（企业登记安装地址、网关位置或真正的定位数据）。
- 固定 HTTPS 部署资源及是否需要真实短信/微信通知；这些是独立外部依赖。

这些材料未齐也可先完成视觉原型与模拟闭环，但不能据此承诺真实设备接入日期。

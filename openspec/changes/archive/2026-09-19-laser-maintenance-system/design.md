# Design: 激光设备售后维修维保系统

## Context

激光设备维保业务需要连接客户、工程师、客服三方，实现报修-派单-维修-结算-评价的全链路数字化管理。当前缺乏统一的系统支持，存在派单靠人工、提成计算不透明、配件库存信息不对称等问题。详见 proposal.md。

## Goals / Non-Goals

**Goals:**
- 构建连接客户、工程师、客服三方的移动端 + 后台系统
- 实现工单全生命周期数字化管理
- 建立透明、可追溯的阶梯提成体系
- 提供实时库存查询和智能派单能力
- 实现客户信息分级脱敏，保护隐私

**Non-Goals:**
- 不支持多城市、多网点（后续扩展）
- 不支持设备厂家直接对接（保内维修走线下结算）
- 不支持工程师组队/团队派单

## Decisions

### 1. 移动端技术选型: React Native

**决定**: 客户 App 和工程师 App 均采用 React Native 开发。

**理由**:
- iOS/Android 双平台代码复用，减少开发和维护成本
- TypeScript 与后端 NestJS 技术栈统一，降低团队学习成本
- 成熟生态：Camera（拍照签名）、Maps（高德导航）、Push（极光推送）等库完善
- 微信登录/分享等场景接入微信 SDK 成熟

**替代方案**:
- Flutter：UI 表现力更强，但 Dart 语言学习成本高，团队现有技能不匹配
- 微信小程序：推广成本低，但 Camera、签名等硬件功能受限，不适合工程师端复杂交互

### 2. 后端技术选型: Node.js + NestJS + PostgreSQL

**决定**: 后端采用 NestJS 框架，数据库采用 PostgreSQL。

**理由**:
- NestJS 装饰器写法清晰，模块化架构易于维护
- TypeScript 全栈统一，类型安全
- PostgreSQL 窗口函数支持月度阶梯提成等复杂聚合查询
- Redis 用于 WebSocket 实时通信的 Pub/Sub 机制，以及会话缓存

**替代方案**:
- Spring Boot (Java)：企业级成熟，但较重，团队 Node.js 技能更熟练
- Django (Python)：快速开发，但复杂业务逻辑不如 NestJS 结构化

### 3. 实时通信: WebSocket + 极光推送混合

**决定**: 工程师在线时使用 WebSocket 实时推送；离线时使用极光推送兜底。

**理由**:
- WebSocket 提供低于 500ms 的实时性，适合派单通知等时效敏感场景
- 极光推送覆盖离线状态，不丢消息
- 混合方案兼顾实时性和可靠性

**替代方案**:
- 纯 WebSocket：工程师 App 关闭或网络波动时消息可能丢失
- 纯极光推送：在线状态延迟较高，不适合抢单场景

### 4. GPS 位置上报: WebSocket 自动上报

**决定**: 工程师 App 通过 WebSocket 每 30 秒自动上报 GPS 位置。

**理由**:
- 抢单排序需要实时距离计算，HTTP 轮询延迟太高
- WebSocket 复用连接，开销小
- 断开重连机制成熟

### 5. 支付集成: 微信支付 + 支付宝

**决定**: 预付定金和退款均支持微信支付和支付宝。

**理由**:
- 覆盖绝大多数国内用户
- 企业账户接入门槛低（个体工商户 / 企业认证公众号）
- 退款原路退回机制成熟

### 6. 地图服务: 高德地图 AMap

**决定**: 导航功能集成高德地图。

**理由**:
- 国内市场份额领先，定位精度和覆盖广度最优
- 移动端 SDK 支持 iOS/Android/Web，文档完善
- 路线规划、导航能力强

### 7. 数据脱敏策略

**决定**: 序列号、姓名、手机号、地址按角色分级脱敏。

| 数据项 | 客户 App 可见 | 工程师 App 可见 | 客服后台可见 |

| 序列号 | SN2023****XXX | SN2023****XXX | 全量 |
| 姓名 | 张* | 张* | 全量 |

## Risks / Trade-offs

### 风险 1: WebSocket 长连接稳定性

**风险**: 网络波动时 WebSocket 断开，导致 GPS 位置和推送消息丢失。

**缓解**:
- 实现断线自动重连（指数退避策略）
- 断开超过 2 分钟向客服推送异常预警
- 离线消息通过极光推送兜底

### 风险 2: 微信/支付宝支付回调可靠性

**风险**: 支付回调网络抖动导致订单状态不一致。

**缓解**:
- 支付状态以第三方回调为准，辅以定时对账任务
- 订单状态机设计允许补偿修复

### 风险 3: 库存数据实时性

**风险**: 库存查询与实际出库之间存在时间差，导致接单后配件缺货。

**缓解**:
- 预占机制：接单时预占配件
- 完工出库或取消时释放预占
- 工程师接单前查看库存状态，缺货时与客户协商改约

### 风险 4: 提成计算精度

**风险**: 月末订单并发完成时，定时重置月度统计可能出现竞态。

**缓解**:
- 月度重置使用数据库事务
- 统计以工单完工时间戳为准，不依赖定时器触发

## Migration Plan

### 第一阶段：基础框架搭建

1. 初始化 NestJS 项目，配置 PostgreSQL 和 Redis
2. 设计并创建数据库表结构
3. 实现基础认证模块（JWT + 短信验证码）
4. 实现客户、工程师、设备的基础 CRUD API

### 第二阶段：核心业务开发

5. 实现工单状态机及全流程 API
6. 实现派单引擎（抢单池 + 指定推送）
7. 实现提成计算模块
8. 集成微信/支付宝支付

### 第三阶段：实时功能

9. 实现 WebSocket 服务（位置上报 + 实时推送）
10. 集成极光推送
11. 集成高德地图导航

### 第四阶段：App 开发

12. 开发客户 App（React Native）
13. 开发工程师 App（React Native）
14. 开发客服后台（React + Ant Design Pro）

### 第五阶段：运营支持

15. 运营数据看板
16. 客服绩效统计
17. 系统监控和日志

## Open Questions

1. **短信验证码供应商**: 暂未选定，是用阿里云还是腾讯云？影响登录模块实现。

2. **支付商户主体**: 公司账户还是个人账户？影响支付接入方式和结算周期。

3. **设备初始数据来源**: 设备档案是客服手动录入，还是对接厂家系统批量导入？

4. **客服绩效计算**: 客服是否有绩效工资？与工单分类数量/客户满意度挂钩？

以上问题不影响技术架构和核心业务开发，可在运营细则明确后补充。
